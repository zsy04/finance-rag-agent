## 二、Agent 核心概念

### 2.1 Agent 定义（四要素）

> LLM 是大脑，Agent = 大脑 + 工具 + 记忆 + 自主循环。Agent 开发 = 做"模型以外的一切"（Harness）。

| 要素 | 说明 |
|------|------|
| 大脑（LLM） | 推理决策，唯一不用自己做的部分 |
| 手（工具） | Function Calling / MCP 与外部交互 |
| 记忆（状态） | 短期（任务上下文）/ 长期（跨会话画像） |
| 循环（Loop） | **灵魂**：感知→思考→行动，模型自己决定下一步 |

### 2.2 Agent vs Chatbot

- Chatbot：对话（问一句答一句）
- Agent：完成任务（模型在循环里自主决定要不要查资料/调工具/下一步干什么）
- **工具调用 = 思考的可见证据**：`tool_calls` 是模型隐式决策的产物（"要不要查、查什么、参数是什么"）

### 2.3 Agent Loop（ReAct）

- 每次 LLM 调用输出二选一：`tool_calls`（调工具）或最终回答（出口）
- 循环：LLM 决策 → 执行工具 → 结果回填 → 再决策 → … → 最终回答
- 思考环节不可见原因：①模型不输出思考文本（`create_agent` 只消费 tool_calls/最终文本）②前端只渲染头尾（UX 决策）
- 循环证据：日志 messages 序列 `user → ai(tool_calls) → tool → ai(最终)`
- 真实例子：见 `财务RAG-Agent架构与Loop-论文素材.md` §3（工资 8000 四步循环）

### 2.4 Multi-Agent 光谱

| 档位 | 形态 | 说明 |
|------|------|------|
| ① Workflow | 固定流程 Router 分发 | 无自主决策 |
| ② **分层子代理（本项目）** | 主 Agent 把子 Agent 当工具调用，信息汇聚回流 | Tool-as-Subagent |
| ③ 自由通信 Multi-Agent | A2A 对等协商 | 谷歌协议，MCP 管 Agent-工具、A2A 管 Agent-Agent |

**什么时候才拆自由通信（三标准，须同时满足）**：① 天然可并行 ② 信息量超单个上下文窗口 ③ 任务价值够高付得起数倍 token。**新手最常见的错误是"再加一个 Agent"——上下文在拆分那一刻就断了。**

## 三、技术选型知识

### 3.1 向量数据库全景（选型四维度：部署形态 / 生态 / 检索能力 / 运维成本）

| 库 | 部署 | 混合检索 | 特点 |
|----|------|---------|------|
| Milvus | 分布式集群 | 支持 | 工业级、亿级向量、重组件（etcd+对象存储） |
| **Qdrant（本项目）** | 单机 Docker / 云 | **原生 dense+sparse+RRF** | Rust、payload 过滤强、一条命令 |
| ChromaDB | 嵌入式 | 弱 | Python 优先、原型快 |
| pgvector | PG 扩展 | 不支持 sparse | 复用 PG、零新组件 |
| Weaviate | 单机/分布式 | 模块化 | Go、自带向量化/重排 |
| Pinecone | 纯 SaaS | 支持 | 省事、闭源、贵 |
| sqlite-vec | 嵌入式 | 无 | 极轻、原型级 |
| Faiss | 库非数据库 | 需自管 | 性能怪兽、不负责持久化 |

**为什么 Qdrant（话术）**：① BGE-M3 输出稠密+稀疏双向量，Qdrant 原生 sparse+RRF，pgvector 要自己造轮子 ② Layer 1 元数据预过滤（relevance_tier）Qdrant payload 原生 ③ 单机 Docker 一条命令。**诚实补充：2937 chunks 用 pgvector 也能跑，选 Qdrant 省的是研发时间不是数据量。** Milvus 是杀鸡用牛刀；ChromaDB 太轻；Pinecone 闭源贵；Faiss 不持久化。

### 3.2 知识图谱

- **Neo4j**：Cypher、ACID、图算法、可视化——重型
- **本项目**：20 条关系规则 JSON 索引（两跳推理），可 git 版本化、热更新、零依赖
- **演进路径**：关系到百级 → 先 NetworkX（内存图算法库）→ 再考虑图库（按规模做决策）

### 3.3 Redis 为什么不用

> Redis 价值 = 跨服务节点状态一致性（缓存/分布式锁/会话隔离）。单机单会话无跨服务问题；**用户记忆是资产，需要持久化，不能是 evict 的缓存**。未来多实例部署才引入——提前引入是提前优化。

### 3.4 模型分级为什么没做

> 选 DeepSeek V4 Flash 本身就是分级第一步（便宜档）；子 Agent 与主 Agent 同模型避免**工具协议漂移**（实测踩坑）。未来高频轻任务（意图改写/画像提取）可加更小模型预筛——**按职责分级是规划，不是现状**。

### 3.5 框架层 / 协议层（行业认知）

- 官方 SDK：OpenAI（事实标准）/ Anthropic / Google GenAI
- 第三方：Vercel AI SDK（最推荐入门）、LangChain（老牌抽象重）、CrewAI（多 Agent 协作）、Mastra（TS 全栈）
- 新物种：官方 Agent SDK（Claude Agent SDK / OpenAI Agents SDK）、Agent Runtime（Cloudflare Agents SDK）
- 协议：**MCP**（Agent-工具，USB 类比）、**Skills**（Agent-方法论，渐进式披露：只加载元数据命中才载全文）、**tool_search**（Claude Code 工具索引按需加载）
- **金句：用确定性的基础设施，包住非确定性的模型**

## 四、架构与设计决策

### 4.1 Tool-as-Subagent（本项目核心架构）

- 主 Agent（Supervisor，`create_agent`）+ 计税/社保两个子 Agent（同为完整 Agent，**对外封装为 `@tool` 挂入主 Agent 工具列表**）
- **"工具是 Agent，Agent 也是工具"**：调用即启动，返回即结束，不需要外部连接
- **三个设计理由**：① 领域隔离（独立 prompt/工具集防污染）② 容错（降级 v1.4 复用参数直调引擎 / 绕过检测 v1.5 强制重算）③ 可回退验证（AGENT_MODE=tools + 对拍评测 8/8）
- 与 A2A 区分：信息经主 Agent 汇聚 ≠ 子 Agent 间直接交流

### 4.2 多 Agent 选型评估（结论：不需要自由通信）

| 标准 | 场景 | 判定 |
|------|------|------|
| 天然可并行 | 一次一问，无并行需求 | ✗ |
| 超上下文窗口 | 单问题信息量小 | ✗ |
| 价值够高 | 单用户成本敏感 | ✗ |

功能全景：问答=主 Agent；计算/社保=子 Agent（领域隔离）；指引/材料生成=纯工具（**材料生成最不该上 Agent**——字段映射填表确定性流程）。4 类伪信号（并发→队列、批量→批处理、上下文长→压缩、结果迭代协商→唯一升级信号但先试单 Agent）。

### 4.3 上下文五层架构（prefix caching 友好）

| 层 | 内容 | 更新频率 |
|----|------|---------|
| 层0 系统层 | system prompt（角色+规则+**安全声明**） | 固定 |
| 层1 用户层 | 画像（事实型白名单） | 低 |
| 层2 任务层 | 工具描述（schema） | 固定 |
| 层3 会话层 | 历史消息 + 40K 摘要（keep 20） | 高 |
| 层4 请求层 | 当前 query + 工具返回（guard 瘦身） | 每轮 |

**原则：变化最少放最前**（稳定前缀 = prefix cache 命中）；安全声明放最前（越早越难绕过）。
**记忆三层**：Working（guard 瘦身结果）/ Short-term（会话+摘要）/ Long-term（画像）。
**画像定位**：SQLite 持久化（技术上跨会话可用、登录零返工），**产品上只依赖会话内复用**——架构预留 + 产品克制。

### 4.4 评测体系（四层闭环）

| 层 | 指标 | 结果 |
|----|------|------|
| 检索层 | 60 条 × 12 类场景，Recall@5/MRR/NDCG | 85%，8 轮迭代 67.5%→85% |
| 工具层 | 26 条路由 | 26/26 |
| 生成层 | LLM-as-judge 忠实度/事件触发 | 100% / 100% |
| 多 Agent 层 | 对拍 8+10 | 全绿 |

**要点**：测试集构建要说清"覆盖正常+边界+对抗"；LLM-as-judge 注意**交叉评**（避免自家族偏好）+ judge 低温 + 版本写死；run_all 一键回归。

## 五、安全与防注入（纵深防御三层）

> 防 prompt injection = 自然语言时代的 SQL 注入；不能押注单个模型，要在全链路设防。**安全边界必须做在执行层——Prompt 挡不住 injection。**

### 5.1 三层纵深防御框架

| 层 | 手段 | 本项目落地 |
|----|------|-----------|
| 模型层 | Instruction Hierarchy（System>User>Tool）+ XML 标签隔离 | ✅ 三层标签 `<user_input>`/`<context>`/`<tool_result>` + SAFETY_HEADER 前置声明（对应层级思想） |
| 链路层 | 输入过滤 + 输出校验 + Canary 探针 | ✅ canary 埋点（canary-7f3a9c）+ 输出审计（危险 tool call 检测 + 工具调用日志）；⏭️ 输入正则跳过（中文误伤率高） |
| 应用层 | 最小权限 + 沙盒 + Human-in-the-loop | ✅ 天然最小权限（确定性工具、无外网/无高危写操作）；HITL 未来接入高危动作（自动代申报）时引入 |

### 5.2 已落地代码清单（2026-08-11）

| 文件 | 改动 |
|------|------|
| `agent/prompts.py` | SAFETY_HEADER（安全声明 + canary 埋点） |
| `agent/engine.py` | system_prompt = SAFETY_HEADER + SYSTEM_PROMPT（放最前） |
| `routers/chat.py` | 用户输入 `<user_input>` 包裹；`_audit_security()`（canary 检测 + 注入告警 + 工具审计日志） |
| `tools/search_knowledge.py` | 检索文本 `<context>` 包裹 |

### 5.3 威胁模型与边界

- 注入面小：知识库官方清洗入库、工具确定性计算、无用户文件上传
- **未来高危面**：PDF 上传解析（间接注入）——实施前必须先评估
- 明确不做：注入测试集（低危面不值得维护）、输入正则（误伤风险）——**规模决策**

## 六、面试话术精华（问答卡片）

### 6.1 双重灵魂拷问

**Q：豆包就能答，为什么做这个？（五连）**
> 豆包是碎片化的：① 不会把计算—政策—申报串成完整链路 ② 不对数字负责（幻觉）③ 没有 2026 新政和郑州细则 ④ 不会带人走完整申报流程 ⑤ 给不出可直接用的产出（申报表 xlsx）。我的系统五件事闭环，件件确定性支撑。

**Q：Claude Code 装个 Skill 就能做，为什么？**
> Skill 给程序员（知道查哪部法填哪个表）；我的产品给零基础大众（不知道个税和经营所得的区别）——引导式追问 + 分步计算 + 自动填表。**Skill 解决高手少走弯路，我解决小白从零到填对表**——产品层差异。

### 6.2 为什么 RAG（被质疑 2026 还 RAG）

> 口语检索（"工资8000扣多少税"→语义映射）+ 溯源（文号证据链）+ 可更新（换知识库不动代码）。Claude Code 用 grep 是因为用户会写关键词，我的用户不会。
**LLM Wiki 为什么没做**：法规要保真、wiki 化丢精度；JSON 关系索引是轻量版。

### 6.3 选型问答（Qdrant/图谱/Redis/模型分级）→ 见 §3 话术

### 6.4 Multi-Agent 定位（核心防线）

> 分层 Agent（Tool-as-Subagent）：主 Agent 调度、子 Agent 结果回流、子 Agent 间不直接通信。三理由：领域隔离/容错/可回退验证。A2A 是对等协议，我的子 Agent 是被调用的工具。**三段式结论：不需要自由通信——三标准全不满足；按需演进，不提前堆复杂度。**

### 6.5 上下文/记忆/评测/安全 → 见 §4.3 / §4.4 / §5 话术（安全三层答法见方案文档 §5）

### 6.6 表达原则

先结论后细节 30 秒切入核心；多用术语（prefix caching / RRF / Tool-as-Subagent / LLM-as-judge / BYOK）；每个"为什么"答出"不是 X 而是 Y"；不会就承认不硬撑。

### 9.1 观测与调试（LangSmith 决策，2026-08-11）

**LangSmith 是什么**：LangChain 官方 LLM 可观测平台——环境变量自动 trace（模型调用/工具执行可视化时间线）、调试、评测、监控；SaaS 云版 + Docker 自托管。

**为什么不接（规模决策）**：
1. 演示环境要离线可控（答辩现场网络不可依赖）
2. 数据不想上云（本地演示项目）
3. trace 需求很轻（每轮工具调用 + token + 失败重试），自建 JSONL 就够

**现状与替代**：
- ✅ **已落地（2026-08-11）**：`backend/context/trace.py` 轻量 JSONL trace——一行一事件（request_start / tool_call / tool_result / request_error / request_end），输出 `backend/data/trace/{日期}.jsonl`，线程安全、失败不影响主流程；`chat.py` 集成 5 类事件 + 耗时统计
- ✅ **已落地**：`chat.py` 工具审计日志（`_audit_security()`，canary 检测 + 注入告警 + 工具调用清单）
- **Langfuse**（开源、Docker 一条命令、国内友好）是团队化开发时的首选替代，优于 LangSmith 云版

## 十、一句话总结（本项目最值钱的一句话）

> **"用确定性的基础设施，包住非确定性的模型"**——金额走代码引擎、政策走法规库检索、流程走指引工具、产出走字段映射填表，LLM 只负责理解与调度。所有技术决策（Qdrant/JSON 图谱/Tool-as-Subagent/防注入标签）都服务于这条原则，所有"没做"的（Redis/Neo4j/A2A/长期画像）都是按规模做的克制取舍。
