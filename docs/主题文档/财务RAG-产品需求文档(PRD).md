## 一、产品概述

### 1.1 一句话定义

**面向零财务基础大众的 AI 财税生活助手**——用自然语言问答替代复杂的税务软件，让每个人都能看懂自己的税、算对自己的钱、填对申报表。

（来源：产品定义与答辩策略、毕业设计综合文档）

### 1.2 项目名称与定位

- **项目名称**：财务 RAG Agent —— 面向零财务基础大众的 AI 财税生活助手
- **产品定位**：用自然语言对话替代复杂的税务软件，让普通人看懂自己的税、算对自己的钱、填对申报表（毕业设计综合文档 §1.2 表述）
- **项目仓库**：github.com/zsy04/finance-rag-agent
- **文档类型与决策日期**：产品定义 | 决策日期 2026-07-26 | 更新 2026-07-31 | 项目：毕设
- **文档定位**：答辩 PPT 的内容来源，回答"做了什么、为什么做、怎么做的、有什么亮点"（来源：产品定义与答辩策略）

### 1.3 核心数据（产品现状）

| 指标 | 数值 |
|------|------|
| 知识库规模 | 115+ 份文档，2937 个向量化知识块 |
| RAG 召回率 | Recall@5 = 77.5%（40/40 全通过） |
| Agent 工具数 | 8 个 @tool + 双子 Agent（计税/社保子 Agent） |

（来源：毕业设计综合文档 §1.3）

### 1.4 核心产品亮点（竞品差异化点）

> 本 PRD 收录两版亮点清单：毕业设计综合文档 v2.0 的 10 条（最新版，Agent 工具数已升级为 8 个），并在每条下方合并产品定义与答辩策略中 8 条的"答辩一句话解释 / 为什么要做"表述。

| # | 亮点 | 说明 / 答辩一句话解释 | 为什么要做 |
|:--:|------|------|-----------|
| ① | **计算不走 LLM** | "税率计算调用 JSON 税率表 + Pydantic 纯函数，LLM 只组织语言。不是 AI 猜数字，是精确计算。" | 涉及金钱，一个数字都不能错 |
| ② | **四层分层召回** | "元数据预过滤 → Qdrant Dense+Sparse 混合检索 RRF 融合 Top-20 → BGE-Reranker Cross-encoder 精排 Top-5 → 轻量知识图谱关系扩展。四层逐层收敛。" | 财税回答需要高度准确，不能答非所问 |
| ③ | **Agent 自治调度** | LangChain create_agent + 8 个 @tool 自动选、自动调。用户一句话"工资8000郑州税多少"→ Agent 自动调上下文工具→个税工具→返回结果卡片，全程零人工干预。 | 真正的 Agent，不是固定的 if-else 流程 |
| ④ | **SSE 事件体系** | 8 种 SSE 事件：thinking / step / result / source / disclaimer / context / error / done。后端 astream_events 精确映射，前端 asyncGenerator 逐帧消费。（产品定义版为 7 种：thinking/step/result/source/disclaimer/error/done，v2.0 后新增 context 事件） | 流式体验不是黑盒，每个阶段用户都能感知 |
| ⑤ | **分步计算 + 法规溯源** | "每个计算结果附带逐步推导过程和法规文号引用。用户看得懂、信得过。" | 零基础用户需要"知其所以然" |
| ⑥ | **双入口 + 多视图** | "对话引导降低新手门槛，快捷表单提升老手效率——React + shadcn/ui 多视图（对话/税率计算器/申报表），左侧导航一键切换。覆盖零基础到熟练用户。" | 同一产品服务不同经验水平的用户 |
| ⑦ | **GPT 表格 + Markdown 渲染** | "AI 回复中的表格（租房扣除三档标准等）用 remark-gfm 正确渲染，带斑马纹、表头高亮，不是纯文本表格符号。所有回复支持标题、列表、代码块、引用等完整 Markdown。" | 财税数据表格化呈现是高频场景，必须正确渲染 |
| ⑧ | **轻量知识图谱** | "20 条精选关联规则 + JSON 驱动，支持双向遍历和两跳推理——个税法→实施条例→专项扣除细则，全链路自动关联。零数据库依赖。" | 纯 RAG 丢失法条交叉引用，知识图谱补齐多跳推理 |
| ⑨ | **上下文工程** | 历史摘要（trigger 40K）+ 工具返回瘦身，judge 忠实度 100%，评测驱动迭代 | 长对话不爆窗、压缩不丢关键信息 |
| ⑩ | **Multi-Agent 化** | 计税/社保双子 Agent，AGENT_MODE 一键回退，失败降级 + 绕过检测，三层评测全绿 | 领域隔离降低 prompt 相互污染、工具权限收敛 |

（来源：毕业设计综合文档 §六、产品定义与答辩策略 §五）

## 二、目标用户与画像

### 2.1 四类目标用户

| 用户类型 | 典型场景 | 核心需求 |
|---------|---------|---------|
| **打工人** | 看不懂工资条上的税和社保扣款 | "我的税算对了吗？""租房能扣多少？" |
| **自由职业者** | 接私活/兼职不知道要不要交税、怎么交 | "这笔劳务费税后到手多少？""要不要申报？" |
| **个体户** | 开了个小店，不知道要交什么税 | "个体户要交哪些税？""怎么网上报税？" |
| **小企业主** | 刚注册公司，财税知识为零 | "小规模纳税人有什么优惠？""增值税怎么报？" |

（来源：产品定义与答辩策略 §三；毕业设计综合文档 §3.1 为同表精简版，已合并）

### 2.2 用户故事：小王（答辩开场 30 秒素材）

> 答辩开场 30 秒讲这个故事。

小王在郑州工作，月薪 8000 元，租房住。工资条上每个月都扣税和社保，但他从来搞不清楚"到底怎么算的"。个税 APP 点进去一堆专业术语——"综合所得""专项附加扣除""累计预扣"——完全看不懂。

他打开「财务 RAG Agent」，在对话框里打字：

> "我工资 8000，在郑州，租房，一个月交多少税？"

系统自动识别他在郑州，引导他补充租房信息。30 秒后，屏幕上逐字流出了答案：

> 你的应纳税所得额 = 年收入 96000 - 起征点 60000 - 社保 12672 - 住房租金扣除 18000 = **5328 元**，适用 3% 税率，全年应纳税 **159.84 元**，每月约 **13.32 元**。
>
> 📎 依据：《个人所得税法》附表一；国发〔2023〕13号。

小王第一次看懂了工资条上的税是怎么算出来的。他接着问："帮我生成申报表"，系统自动填好了个人所得税年度申报表，还附带了一份空白原表供他下载核对。

（来源：产品定义与答辩策略 §二）

### 2.3 用户痛点分析（产品立项依据）

我国税收体系复杂，普通大众面临以下困难：

- **术语门槛高**："综合所得""专项附加扣除""累计预扣法"等专业词汇难以理解
- **信息碎片化**：政策分散在税总官网、12366 热线、个税 APP 等多处，查找困难
- **计算不透明**：工资条上的扣款数字来源不明，用户无法自行验证
- **操作门槛高**：年度汇算清缴、申报表填写等操作需要一定的财税基础

（来源：毕业设计综合文档 §2.1）

## 三、需求背景与知识域

### 3.1 需求背景：现有方案的不足

| 现有方案 | 不足 |
|---------|------|
| 个税 APP | 功能齐全但术语密集，零基础用户难以理解 |
| 搜索引擎 | 结果零散、权威性不可控、需要用户自行判断 |
| 财税咨询 | 成本高（付费）、时效差（需预约） |
| 通用 AI 助手 | 知识不专业（可能编造税率）、无法精确计算 |
| 企业税务软件 | 面向企业，个人场景不适配，操作复杂 |

（来源：毕业设计综合文档 §2.2）

### 3.2 项目意义

1. **社会价值**：降低财税知识的获取门槛，帮助普通大众合理纳税、享受税收优惠
2. **技术验证**：探索 RAG + Agent 在垂直领域的可行性，验证"准确性优先"的设计哲学
3. **学术价值**：完整的评测体系（RAG 检索 + Agent 工具选择），可作为同类研究的参考基线
4. **个人成长**：验证"个人 + AI = 可落地工程"的开发范式，形成可迁移的方法论

（来源：毕业设计综合文档 §2.3）

### 3.3 知识域总览

> **目标用户**：零财务基础的大众用户（打工人、自由职业者、个体户、小企业主）
> **核心场景**：税务计算、申报指引、发票知识、社保公积金、日常财务概念
> **知识层级**：以"能用、能算、能看懂"为标准，不做学术/准则层面的深度覆盖
> **后续文档**：→ `财务RAG-MVP资料收集执行表.md`（70项清单+链接）→ `财务RAG-资料收集预处理方案.md`（执行方案）→ `财务RAG-技术架构与Agent方案.md`（系统设计）

（来源：资料收集蓝图 开头元信息）

| 二·社保与公积金（仅次于个税的高频场景） | #14-#20 | 模块一 智能问答 + 模块二 税率计算 |

MVP 四大功能与资料模块对应关系（来源：MVP资料收集执行表）：

| MVP 功能 | 对应资料模块 | 模块定位 |
|---------|------------|---------|
| 智能问答 | 模块一（RAG 通用知识底座） | 回答用户各种各样的财税问题，覆盖面要广，不追求每条都极致精确，但求"有问可答" |
| 税率计算 | 模块二（结构化数据） | 结构化格式存储（JSON/CSV/结构化 Markdown 表格），计算功能不能依赖 LLM 的数学能力，需要程序直接读取数据来计算 |
| 申报指引 | 模块三（操作流程知识） | Step-by-Step 的操作指南，最好是图文并茂的官方操作手册 |
| 申报材料生成 | 模块四（模板+规则） | 用户填完个人信息后，Agent 自动生成申报材料；需要收集申报表模板和填报规则 |

## 四、MVP 功能需求

### 4.1 功能矩阵（6 功能 → Agent 动作）

| 功能 | 用户怎么说 | Agent 怎么做 |
|------|-----------|-------------|
| **智能问答** | "租房扣除标准是多少？" | Agent 调 `search_knowledge` → 四层分层召回 → BGE-M3 混合检索 + Reranker → DeepSeek 流式回答 + 来源链接 |
| **税率计算** | "工资 8000 郑州交多少税？" | Agent 调 `calculate_income_tax` → JSON 税率表代码计算（不走 LLM）→ 结果卡片 (tax_result) + 分步推导 + 法规引用 |
| **社保计算** | "郑州社保单位和个人各交多少？" | Agent 调 `query_social_insurance` → JSON 社保数据代码计算 → 结果卡片 (social_result) + 逐险种明细 |

**Multi-Agent 机制**（P1，2026-08-05 完成，来源：毕业设计综合文档 §5.5）：

> 设计见《财务RAG-Multi-Agent 集成设计文档》v1.5。把计税/社保两个领域升级为独立子 Agent（Tool-as-Subagent 模式），验证"单 Agent → 多 Agent"改造路径。

| 机制 | 说明 |
|------|------|
| 双子 Agent | `tax_subagent` / `social_subagent`，独立 system prompt + 画像读写 + 领域工具；无 checkpointer 无历史、全局单例，包成 tool 挂回主 Agent |

### 5.1 B 表定位

B 表 = 个人所得税基础信息表（B表），面向**个体工商户**经营所得申报。和 A 表（雇员）共用同一套申报流程，不同的是计税逻辑和字段。

### 5.2 与 A 表的核心差异

| 对比维度 | A 表 | B 表 |
|----------|------|------|
| 适用人群 | 雇员（有扣缴义务人） | 个体工商户 / 自由职业者 |
| 任职受雇从业信息 | 必填 | **不填** |
| 被投资单位信息 | 不填 | **填自己的个体工商户名称 + 信用代码** |

| 是否有工资 | 有 | **无** |
| 计税逻辑 | 工资 - 社保 - 专项扣除 - 起征点 | 收入 - 成本(含房租) - 社保 - 专项扣除 - 亏损 |

（来源：B表-个体工商户申报需求）

### 6.9 SSE 事件体系（前后端交互事件契约）

前端依赖后端通过 SSE 发送以下事件类型（v2.0 为 8 种；产品定义 v1.0 为 7 种，不含 `context`）：

| 事件类型 | 触发时机 | 数据格式 | 前端行为 |
|---------|---------|---------|---------|
| `thinking` | Agent 开始处理 | `{"message": "正在为您计算……"}` | 显示加载提示 |
| `step` | 计算过程中每一步 | `{"content": "月薪8000×12=年收入96000元"}` | 流式追加到 AI 气泡 |
| `confirm` | 需要用户确认的节点 | `{"question": "租房扣除按1500元/月?", "options": ["确认","自己填"]}` | 暂停流式，显示交互按钮 |
| `result_card` | 计算完成 | `{"card_type": "tax_result", "data": {...}}` | 插入结果卡片 |
| `source` | RAG 检索来源 | `{"title": "…", "url": "…"}` | 折叠展示来源链接 |
| `disclaimer` | AI 免责 | `{"content": "本结果由AI辅助计算……"}` | 回复末尾灰色小字 |
| `context` | 历史摘要发生时 | 摘要提示 | 下一轮流开始时提示"较早的对话已归档…"，前端 📦 提示条 |
| `error` | 处理失败 | `{"message": "回答失败了，请重试"}` | 错误气泡 + 重试按钮 |
| `done` | 回复完成 | `{}` | 恢复输入框可用 |

（来源：UI 设计方案 §六、毕业设计综合文档 §5.4）

### 7.2 时效性

1. **时效性是生命线**：个税专项扣除标准、社保基数、小微企业优惠额度每年都在变，过期资料比没有资料更危险
2. 每条资料标注：来源、发布时间、适用范围（全国/地方）、时效性标记；税率/扣除标准类数据要有版本标记，支持热更新替换旧版本 chunk
3. **毕设关键提醒**：小规模纳税人增值税 1% 优惠到 2027.12.31，个税专项扣除标准可能再调整。每个 chunk 的 metadata 必须带 `effective_date` 和 `expiry_date`

（来源：资料收集蓝图 · 资料格式建议/关键提醒；MVP资料收集执行表 · 毕设关键提醒）

### 7.3 地域差异标注

1. **地域差异要标注**：社保缴费比例、公积金基数、契税优惠等各地不同，资料必须标注适用省市
2. **知识库双层架构**（全国统一层 + 城市覆盖层）：后续新增城市只需在 `cities/` 下按相同 schema 追加文件，全国层（模块一~四）不动：

**Agent 查询路由逻辑**：

1. 识别用户问题是否涉及地域参数（社保/公积金/医保/操作流程 → 大概率命中城市层）
2. 若涉及 → 从用户上下文或输入中提取城市代码 → 路由到 `cities/{city}/` 对应文件
3. 若不涉及 → 从 `national/` 检索
4. 同一次回答中允许**双层混合检索**（如"郑州个税怎么报" = 个税法从 national 取 + 操作入口从 cities/zhengzhou 取）

### 7.4 计算不走 LLM

**根决策：准确性优先**——财税场景下，错了比慢了严重得多。由此引出三条刚性约束：

1. 税费计算不走 LLM 推理（数据驱动，JSON + Pydantic）
2. 知识检索必须命中真正法条原文（不能靠语义相似度蒙混）
3. 输出必须带法规溯源 + AI 免责声明

（来源：产品定义与答辩策略 §8.1）

**落地规则**：

- **税率表别让 LLM 算**：税率计算走代码逻辑读取 JSON，不要依赖 RAG 检索 + LLM 推理——算错一个数答辩直接翻车
- **申报材料生成 = 表单字段映射**：本质是把用户输入的 key-value 填入申报表模板对应字段，逻辑可比做"智能填表"而非"AI 写文档"，更容易控制准确性
- 计算类要配公式：税率表、扣除标准等必须结构化存储（表格/JSON），方便 agent 调取计算而不依赖 LLM 的算力

（来源：MVP资料收集执行表 · 毕设关键提醒；资料收集蓝图 · 关键提醒）

**关联说明（技术实现，来源：产品定义与答辩策略 §8.3）**：Reranker 的副作用——Cross-encoder 重排可能把原本 top-1 的文档刷到 30 名开外（只看 query-document 细粒度匹配，而非全局语义）。解法是**权重锚定**（`final_score = rerank × weight/10.0`）+ **场景取舍**（个人财税场景下年终汇算 > 股权激励）。

### 7.5 结构化存储原则

**资料格式建议**：

| 维度 | 建议 |
|------|------|
| **格式** | 优先 Markdown（结构化强，易分块），其次 PDF（需 OCR 预处理），不推荐纯扫描件 |
| **分块策略** | 按"知识点单元"分块，每个 chunk 对应一个独立问答（如"住房租金扣除标准" = 一个 chunk） |
| **元数据** | 每条资料标注：来源、发布时间、适用范围（全国/地方）、时效性标记 |
| **语言风格** | 优先收集官方"图解""解读""即问即答"类材料——本身就以小白视角写的，RAG 检索匹配度最高 |
| **更新机制** | 税率/扣除标准类数据要有版本标记，支持热更新替换旧版本 chunk |

### 9.4 关联说明：项目复盘核心发现（答辩深度追问素材，来源：产品定义与答辩策略 §8.4/§8.5）

**AI 编码协作模式**：发现单一 AI 自审查不可靠（倾向正向评价），采用**双 AI 交叉审核**：WorkBuddy 出方案+代码，Trae 独立审查。本质和 Reranker 加权重锚定是同一个逻辑——不能让单一裁判决定一切。

**方法论提炼：SPU 流程**：

- **S (Scope)**：先瞄准用户 → 固定核心约束 → 确定评测尺度
- **P (Process)**：先跑通 → 测 bad case → 建评测覆盖 → 诊断根因 → 修复 → 再测（防过拟合）
- **U (Utility)**：性价比驱动选型，不追最强追最可控

> "初始基线 Recall@5 只有 67.5%，4 条 query 完全搜不到正确答案。我做了一个逐条根因诊断——不是盲目调参数，而是分析每条失败背后的语义失配模式。最终通过 Query 改写层、DOC_KEYWORDS 关键词注入、QA 文档结构修复、分层权重管理四套机制，将 Recall@5 提升到 77.5%、MRR 到 0.83、40 条评测全部命中。整个优化过程没有加一条硬编码规则，全部是通用机制。"

**优化中形成的可复用资产（5A.5）**：

| 机制 | 文件 | 用途 |
|---|---|---|
| Query 改写层 | `backend/rag/query_rewriter.py` | 50+ 条口语→术语映射，Key 长度降序匹配，6 词扩展上限 |
| DOC_KEYWORDS | `scripts/embed_and_upsert.py` | 5 个关键文档的关键词注入，同时写入向量和 Reranker 可见内容 |
| WEIGHT_OVERRIDES | `scripts/embed_and_upsert.py` | 关键文档权重管理表，重嵌时自动生效 |
| QA 结构修复 | `scripts/fix_qa_headings.py` | 批量 QA 文档 `##` 标题规范化脚本 |
| 评测体系 | `backend/eval/` | 40 条评测集 + 4 指标自动化脚本 |
| 轻量知识图谱 | `rag-data/relations.json` + `backend/rag/retriever.py` | 20 条关联规则，双向遍历 + 两跳推理，零数据库依赖 |

| "为什么不用大厂现成的 Agent 方案？" | 个人 vs 大厂的坐标系不同，他们面向已有业务系统做嵌入，我面向从零开始的 AI 原生设计 |

| "你从这个项目学到了什么？" | 开发者的核心竞争力是决策能力——选什么、往哪走、在哪妥协、在哪死守 |
| "上下文工程具体解决什么问题？" | 两处硬伤：工具返回硬截断丢关键数字、长对话无限膨胀爆窗。解法：提取式瘦身（必保数字/文号）+ 历史摘要（trigger 40K），judge 忠实度 100% 证明压缩不丢信息 |
| "为什么做 Multi-Agent？值不值？" | 验证"单 Agent → 多 Agent"改造路径：领域隔离降低 prompt 相互污染、工具权限收敛。代价是延迟 +20-40%，所以保留 AGENT_MODE 一键回退，演示可控 |
| "双子 Agent 和 Supervisor 模式的区别？" | 我用的是 Tool-as-Subagent（轻量）：子 Agent 包成 tool 挂回主 Agent，无 checkpointer 无历史、全局单例；Supervisor 是显式路由分发，langgraph-prebuilt 1.1.0 无 create_supervisor 需自建 StateGraph，作为后续演进方向 |
