## 1. 数据规划总览

> 来源文档：`财务RAG-资料收集蓝图.md`、`财务RAG-MVP资料收集执行表.md`

### 1.1 项目定位与数据设计约束

- **目标用户**：零财务基础的大众用户（打工人、自由职业者、个体户、小企业主）
- **核心场景**：税务计算、申报指引、发票知识、社保公积金、日常财务概念
- **知识层级**：以"能用、能算、能看懂"为标准，不做学术/准则层面的深度覆盖
- **MVP 四大功能**：智能问答 · 税率计算 · 申报指引 · 申报材料生成
- **范围**：全国统一政策 + 地方扩展（已内置河南郑州，后续城市可插拔）
- **格式策略**：原文为 PDF → 保留 PDF；其余 → Markdown；地方数据 → JSON 结构化

### 1.2 知识域 7 大分类

> 来源文档：`财务RAG-资料收集蓝图.md`（知识域框架 51 项主题，详见第 2 章"主题层清单"）

| 知识域 | 内容范围 | 用户场景 |
|--------|---------|---------|
| 一·个人所得税 | 综合所得 / 经营所得 / 其他分类所得 | 最核心、最高频：算税、退税、年终奖、劳务报酬 |
| 二·社保与公积金 | 五险一金框架、缴费比例、医保报销、养老金、公积金提取、灵活就业社保 | 仅次于个税的高频场景：工资条、看病、退休 |
| 三·小企业与个体户税务 | 主体选择、纳税人类型、增值税优惠、企税优惠、税种申报周期、发票 | 创业/副业刚需 |
| 四·日常财务概念普及 | 收入成本利润、含税价、税率速查、发票图谱、报销、对公账户 | 财务常识扫盲区 |

### 1.3 双层知识库架构

> 来源文档：`财务RAG-MVP资料收集执行表.md`（架构原文）

**双层设计**：`national/` 全国统一层（模块一~四，不可变）+ `cities/` 城市覆盖层（模块五，可插拔）。后续新增城市（北京/上海/深圳等）只需在 `cities/` 下按相同 schema 追加文件，全国统一层（模块一~四）不动。

```
RAG 知识库结构
├── national/                   # 全国统一政策（模块一~四，不可变）
│   ├── tax_law/               # 个人所得税法、增值税法等
│   ├── social_insurance_law/  # 社会保险法（法律层面）
│   ├── rates/                 # 全国统一的税率表 JSON
│   ├── filing_templates/      # 申报表模板 DOC/PDF
│   └── qa_corpus/             # 即问即答语料
│
├── cities/                    # 城市差异化覆盖（模块五，可插拔）
│   ├── zhengzhou/
│   │   ├── social_insurance.json   # 社保缴费比例+基数
│   │   ├── housing_fund.json       # 公积金政策
│   │   ├── medical_reimbursement.md  # 医保报销规则
│   │   ├── tax_operations.md       # 地方税务操作指引
│   │   └── local_policies.md       # 其他地方政策（Phase 2）
│   │
│   ├── beijing/               # 后续添加...
│   ├── shanghai/              # 后续添加...
│   └── _template/             # 新城市接入模板
│       ├── social_insurance.schema.json
│       └── housing_fund.schema.json
│
└── metadata/
    └── cities_index.json      # 城市索引：city_code → 政策版本号 + 生效日期
```

### 1.4 Agent 查询路由逻辑

> 来源文档：`财务RAG-MVP资料收集执行表.md`

1. 识别用户问题是否涉及地域参数（社保/公积金/医保/操作流程 → 大概率命中城市层）
2. 若涉及 → 从用户上下文或输入中提取城市代码 → 路由到 `cities/{city}/` 对应文件
3. 若不涉及 → 从 `national/` 检索
4. 同一次回答中允许**双层混合检索**（如"郑州个税怎么报" = 个税法从 national 取 + 操作入口从 cities/zhengzhou 取）

### 1.5 资料格式总体建议

> 来源文档：`财务RAG-资料收集蓝图.md`（资料格式建议）

| 维度 | 建议 |
|------|------|
| **格式** | 优先 Markdown（结构化强，易分块），其次 PDF（需 OCR 预处理），不推荐纯扫描件 |
| **分块策略** | 按"知识点单元"分块，每个 chunk 对应一个独立问答（如"住房租金扣除标准" = 一个 chunk） |
| **元数据** | 每条资料标注：来源、发布时间、适用范围（全国/地方）、时效性标记 |
| **语言风格** | 优先收集官方"图解""解读""即问即答"类材料——本身就以小白视角写的，RAG 检索匹配度最高 |
| **更新机制** | 税率/扣除标准类数据要有版本标记，支持热更新替换旧版本 chunk |

## 5. 元数据标准

> 来源文档：`财务RAG-资料收集预处理方案.md`（决策 D6、frontmatter 示例、manifest.json）、`资料格式规范.md`（frontmatter 规则）

### 5.1 YAML frontmatter 字段（决策 D6）

每个 `processed/` 下的 `.md` 文件**必须以 YAML frontmatter 开头**，字段定义（决策 D6）：

| 字段 | 含义 | 示例 |
|------|------|------|
| `source_url` | 来源链接 | https://fgk.chinatax.gov.cn/... |
| `doc_number` | 文号 | 主席令第9号 |
| `effective_from` | 生效日期（清洗脚本自动从"成文日期"提取） | 2018-08-31 |
| `expiry_date` | 失效日期（时间敏感数据必填） | 2027-12-31 或空 |
| `module` | 所属功能模块 | 一 |
| `category` | 资料类别 | tax_law |
| `city` | 适用范围（全国/地方） | national |
| `doc_title` | 文档标题 | 个人所得税法 |
| `relevance_tier` | 相关性层级（🆕） | tax_law / tax_regulation / qa_corpus / general_law |
| `relevance_weight` | 检索权重（🆕） | 10 / 8 / 6 / 3 |
| `cleaned_at` | 清洗时间 | 2026-07-29 |

### 5.2 frontmatter 完整示例

```yaml
---
source_url: https://fgk.chinatax.gov.cn/zcfgk/c100009/c5193028/content.html
doc_number: 主席令第9号
effective_from: 2018-08-31      # 清洗脚本自动从"成文日期"提取
expiry_date:
module: 一
category: tax_law
city: national
doc_title: 个人所得税法
relevance_tier: tax_law          # 🆕 相关性层级（tax_law/tax_regulation/qa_corpus/general_law）
relevance_weight: 10             # 🆕 检索权重（10/8/6/3）
cleaned_at: 2026-07-29
---
```

> 格式规范视角（来源：`资料格式规范.md`）：frontmatter 首尾各一行 `---`，中间字段无特殊要求，**至少包含 `doc_title` 和 `category`**；frontmatter 结束后空一行再开始正文。

## 6. 采集工具链

> 来源文档：`财务RAG-资料收集预处理方案.md`（MarkItDown 评估、执行步骤）、staging 实际产出（MHTML 双变体处理）

### 6.1 clean_to_md.py（MHTML 双变体处理）

staging 层落盘的 119 个原始文件为 **MHTML/.doc 双变体**（不同渠道导出的 MHTML 结构、Word 的 .doc 二进制格式并存）。`clean_to_md.py` 负责把这两类原始变体统一清洗为标准化 Markdown。

**脚本职责**：

| 处理项 | 说明 |
|--------|------|
| 输入 | `staging/` 下的 `.mhtml` / `.mht` / `.doc` 原始文件 |
| MHTML 解析 | 识别两种 MHTML 变体（浏览器导出变体 / 网页存档变体），统一解析内嵌 HTML |
| HTML 清洗 | 清洗 HTML 标签（保留表格结构），移除导航/页眉/页脚/侧边栏噪声 |
| 智能换行 | 按 `##章/###条` 层级输出标准化标题 + 智能换行 |
| 元数据回填 | 从 `metadata.json` 读取 source_url、doc_number、module、category 等，生成 YAML frontmatter |
| 输出 | `processed/` 对应子目录下的 `.md` 文件 |

**工具参数与用法**：

```
# 全量清洗（按 metadata.json 映射批量处理 staging → processed）
python clean_to_md.py --input rag-data/staging --output rag-data/processed \
    --meta rag-data/staging/metadata.json

# 单文件清洗（调试用）
python clean_to_md.py --file rag-data/staging/0056.mhtml --output rag-data/processed

# 指定城市/模块落盘
python clean_to_md.py --input rag-data/staging --output rag-data/processed \
    --module zhengzhou --category social_insurance
```

> 清洗完成后必须验证：表格完整性、特殊符号（‰、{}）、文号、金额数字。

## 7. 切分与向量化

> 来源文档：`财务RAG-资料收集预处理方案.md`（决策 D4：目标 800 tokens/chunk，每个 chunk 为独立 Q&A 单元）、`财务RAG-MVP资料收集执行表.md`（预处理流程：按知识单元分块 500-1500 tokens）

### 7.1 分块策略与目标

- **决策 D4**：分块粒度目标 **800 tokens/chunk**，每个 chunk 为独立 Q&A 单元。
- 蓝图/执行表的分块建议：按"知识点单元"分块（每个 chunk 500-1500 tokens，尽可能独立成问答单元），如"住房租金扣除标准" = 一个 chunk；qa_corpus 按 `## 问句` 的 Q&A 对切分。
- 以 D4 的 800 tokens 为最终目标粒度，与源文档的 500-1500 区间兼容。

### 7.2 切分窗口与重叠

- **窗口参数**：800/80 窗口（chunk 目标 800 tokens，窗口滑步 80 tokens）+ **15% 重叠**（相邻 chunk 保留 15% 边界内容），防止知识单元在边界处被截断。
- 重叠策略使跨 chunk 的语义（如"公式 + 取值规则"）在两段均可见，兼顾检索召回与去重。

### 7.3 chunks.jsonl 中间产物

切分结果以 `chunks.jsonl` 输出为中间产物（每行一个 chunk），字段结构：

```json
{"chunk_id": "tax_law_0001_001", "doc_title": "中华人民共和国印花税法", "source_url": "https://fgk.chinatax.gov.cn/...", "doc_number": "主席令第X号", "module": "一", "category": "tax_law", "city": "national", "relevance_tier": "tax_law", "relevance_weight": 10, "effective_from": "2022-07-01", "expiry_date": null, "text": "……（chunk 正文，约 800 tokens）……", "token_count": 812, "prev_chunk_id": "tax_law_0001_000", "next_chunk_id": "tax_law_0001_002"}
```

- 每行携带完整 frontmatter 元数据，供向量化阶段写入 Qdrant 时保持可溯源。
- 2937 个 chunks 即为本中间产物的最终规模。

### 7.4 语义边界切分原则

1. **知识单元独立成块**：一个 chunk 对应一个独立问答/一个知识点（如一条法律条文、一条专项扣除标准、一个操作步骤）。
2. **Q&A 对切分**：qa_corpus 以 `## 问句` 为边界整对切分，问题与答案不拆散。
3. **层级优先**：优先在 `## 章` / `### 节` / `## 第X条` 的标题边界处切分，不硬切正文段落。
4. **公式与规则同块**：计算公式与每一步的取值规则保持在同一个 chunk 内。
5. **窗口兜底**：语义边界不足 800 tokens 时以窗口兜底，配合 15% 重叠补边界。

### 7.5 切分产出

| 项目 | 数值 |
|------|:---:|
| 目标 chunk 粒度 | 800 tokens |
| 窗口参数 | 800/80 + 15% 重叠 |
| 中间产物 | chunks.jsonl（逐行全量元数据） |
| 切分结果 | **2937 个 chunks** |

## 8. Markdown 格式规范（全文收录）

> 来源文档：`资料格式规范.md`（全文原文，一字不删）
> 适用范围：所有 `processed/national/tax_law/` 下的 `.md` 文件。基于车船税法、烟叶税法、印花税法、增值税法四个文件的格式总结。

### 8.1 文件结构总览

```
---
（YAML frontmatter）
---

# 法律全称

## 注释

（修正历史，一段或多段）

（如有目录，见下方 8.4）

## 第X条　（正文）

...

## 附：（如有附件）

附件文件名
```

### 8.2 逐项规范

#### 8.2.1 YAML Frontmatter

首尾各一行 `---`，中间字段无特殊要求，至少包含 `doc_title` 和 `category`。

```yaml
---
source_url: https://fgk.chinatax.gov.cn/...
doc_number: 主席令第X号
effective_from:
expiry_date:
module: 一
category: tax_law
city: national
doc_title: 印花税法
cleaned_at: 2026-07-27 17:08:42
---
```

**规则**：frontmatter 结束后空一行再开始正文。

#### 8.2.2 法律标题

```markdown
# 中华人民共和国印花税法
```

- H1（一个 `#`），法律全称。
- 不是"印花税法"而是"中华人民共和国印花税法"。
- 标题后空一行。

> 例外：非"法"类文件（如"关于惩治虚开……的决定"）标题用原完整名称，不加"中华人民共和国"前缀。

#### 8.2.3 注释（修正历史）

```markdown
## 注释

2021年6月10日第十三届全国人民代表大会常务委员会第二十九次会议通过
```

- `## 注释` 为 H2。
- 下一行为通过/修正日期，一段文字，不拆行。
- 如果有多条修正记录，用全角空格 `　` 分隔。
- 注释节后空一行。

#### 8.2.4 目录（如有）

```markdown
## 目录

第一章　总　　则

第二章　税　　率

...
```

- `## 目录` 为 H2。
- 目录列为普通段落文本，不加序号。
- 章名使用全角空格 `　` 分隔，不加 `## `。
- 目录节后空一行。

#### 8.2.5 章标题（如有）

```markdown
## 第一章　总　　则
```

- `## 第X章　XXX` 为 H2。
- 章名中的空格用 `　`（全角空格 U+3000）。
- 章标题后空一行。

#### 8.2.6 节标题（如有）

```markdown
### 第一节　纳税人
```

- `### 第X节　XXX` 为 H3。
- 节标题末尾带全角空格。
- 节标题后空一行。
- 章 → 节 → 条的层级为：H2 章、H3 节、H2 条。

#### 8.2.7 条（法律条文）

**格式 A：条标题 + 正文分两行**

```markdown
## 第一条　

在中华人民共和国境内书立应税凭证、进行证券交易的单位和个人，为印花税的纳税人...
```

- `## 第X条　` 为 H2（末尾带全角空格）。
- 正文从下一行开始，普通段落。

**格式 B：条标题 + 正文同行（仅当条文字数少时）**

```markdown
## 第四条　烟叶税的税率为百分之二十。
```

- 条标题后直接跟正文，中间用全角空格。

**选择规则**：正文超过 50 字用格式 A，少于 50 字可用格式 B。同文件内保持一致。

**层级关系**：无论条文处于章还是节之下，`第X条` 始终用 `##`（H2）。章 H2 → 节 H3 → 条 H2，节的存在不改变条的层级。

#### 8.2.8 条内列表

**错误写法**（不要用 H3 子标题）：

```markdown
### （一）工资、薪金所得；     ← 错误
```

**正确写法**（用数字序号）：

```markdown
## 第三条　下列车船免征车船税：

1. 捕捞、养殖渔船；

2. 军队、武装警察部队专用的车船；

3. 警用车船；
```

- 用 `1. 2. 3.` 数字列表，不用 `（一）（二）（三）` 中文序号。
- 每个列表项独立一行，中间空行。
- 列表前不空行（紧跟条标题内容），列表后空一行。

#### 8.2.9 段落间距

- **条与条之间**：`## 第X条` 前应有一个空行。
- **条内段落之间**：空一行。
- **章与节之间**：章标题后空一行，章内第一条前不额外空行。

#### 8.2.10 附件

```markdown
## 附件：

印花税税目税率表.ppt
```

或简写：

```markdown
## 附：

车船税税目税额表.doc
```

- `## 附件：` 或 `## 附：` 为 H2。
- 下一行为附件文件名。

### 8.3 禁止项

| ❌ 不要 | ✅ 应该 |
|---------|--------|
| `### （一）...` 作为子标题 | `1. 2. 3.` 数字列表 |
| `（一）（二）` 中文序号 | `1. 2. 3.` |
| `第一条` 无空格无 `##` | `## 第一条　` |
| 正文与条标题同行但超 50 字 | 正文换下一行 |
| 导航文字（字体大小、微信分享等） | 已在前序清洗中移除 |
| `### 中华人民共和国...` | `# 中华人民共和国...` |

### 8.4 快速检查清单（原文全文）

- [ ] frontmatter 有 `doc_title` 和 `category`
- [ ] `# 标题` 为完整的"中华人民共和国XXX法"
- [ ] `## 注释` 后跟修正历史
- [ ] `## 第X条　` 全部为 H2，末尾有全角空格
- [ ] 条内列表用 `1. 2. 3.`，不用 `（一）（二）`
- [ ] 条与条之间有空行
- [ ] 无导航噪音、无 `###` 子标题
- [ ] 附件用 `## 附件：`

```json
}
```

- `cell` 为申报表模板中的单元格坐标，驱动 xlsx/docx 填表。
- `source_key` 指向 Agent 从用户输入/对话中抽取的字段，`validation` 为填表前的逻辑校验规则。
- templates 目录实际产出：`个人所得税基础信息表（A表）` 与 `（B表）` 各含 `.xlsx + .docx` 填表说明。

### 11.2 官方口径优先

> 来源文档：`财务RAG-资料收集蓝图.md`（关键提醒 3）

- 优先采集税总/人社部/各地税务局官网的官方文件、解读、图解。自媒体文章仅作补充参考。
- 决策 D9：操作指引/即问即答统一锚定河南省税务局官方来源。
- 来源可溯源：答辩时老师必问"你的数据从哪来"，每条答案带上引用链接（每条 chunk 携带 source_url）。

### 11.3 时效性

> 来源文档：`财务RAG-资料收集蓝图.md`（关键提醒 1）、`财务RAG-MVP资料收集执行表.md`（毕设关键提醒 1）

- **时效性是生命线**：个税专项扣除标准、社保基数、小微企业优惠额度每年都在变，过期资料比没有资料更危险。
- 每个 chunk 的 metadata 必须带 `effective_date` 和 `expiry_date`。
- 已知时效锚点：小规模纳税人增值税 1% 优惠到 2027.12.31；郑州社保/公积金数据时效 2025-07-01 至 2026-06-30；个税专项扣除标准可能再调整。

### 11.4 地域标注

> 来源文档：`财务RAG-资料收集蓝图.md`（关键提醒 2）

- 地域差异要标注：社保缴费比例、公积金基数、契税优惠等各地不同，资料必须标注适用省市。
- frontmatter `city` 字段（national/城市名）承担此职责；城市层数据经 `cities_index.json` 管理版本号与生效日期。

### 11.5 计算类不走 LLM

> 来源文档：`财务RAG-资料收集蓝图.md`（关键提醒 4）、`财务RAG-MVP资料收集执行表.md`（毕设关键提醒 2、3）

1. **计算类要配公式**：税率表、扣除标准等必须结构化存储（表格/JSON），方便 agent 调取计算而不依赖 LLM 的算力。
2. **税率表别让 LLM 算**：税率计算走代码逻辑读取 JSON，不要依赖 RAG 检索 + LLM 推理 —— 算错一个数答辩直接翻车。
3. **申报材料生成 = 表单字段映射**：本质是把用户输入的 key-value 填入申报表模板对应字段（form_field_map.json），逻辑可比做"智能填表"而非"AI 写文档"，更容易控制准确性。
