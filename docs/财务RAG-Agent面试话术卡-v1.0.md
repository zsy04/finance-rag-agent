## 0. 一句话定位（开场必背）

> "面向零财务基础大众的 AI 财税助手：自然语言对话，替代复杂税务软件。让每个人**看懂自己的税、算对自己的钱、填对申报表**。核心是三件确定性的东西：**法规原文溯源、纯代码计算引擎、申报表字段映射**——LLM 只负责理解和调度，金额从不出自模型。"

## 1. 双重灵魂拷问

### 1.1 第一问："豆包就能答，为什么做这个？"（五连）

> "豆包能答个税，但它是碎片化的——它不会：
> **① 把'计算—政策—申报'串成完整链路**（系统整合）；
> **② 对数字负责**（会幻觉，错了也不告诉你错在哪）；
> **③ 覆盖 2026 年最新政策和郑州地方细则**（知识滞后）；
> **④ 带你走完整申报流程**（汇算清缴时间节点、个体户季度申报步骤）；
> **⑤ 给你可直接用的产出**（申报表自动填好导出 xlsx）。
> 我的系统把这五件事做成闭环，每件都有确定性的技术支撑——计算走代码引擎、政策走法规库检索、流程走指引工具、产出走字段映射填表。"

### 1.2 第二问："用 Claude Code 装个 Skill 就能解决，为什么做这个？"

> "Skill 是**给程序员用的工具**，前提是你知道要查哪部法、填哪个表；我的产品是**给零基础大众的**——用户不知道'个人所得税'和'经营所得'的区别，需要引导式追问、分步计算、申报表自动填好导出 xlsx。**Skill 解决'高手少走弯路'，我解决'小白从零到填对表'**——这是产品层差异，不是技术层差异。"

## 2. 为什么用 RAG（被质疑"2026 年了还 RAG"时用）

> "我清楚长上下文时代 RAG 不是唯一答案——Claude Code 用 grep 是因为它的用户会写关键词。但我的用户是零基础大众，只会说'我工资 8000 要交多少税'这种口语，所以我的三连理由：
> **① 口语检索**——语义检索才能把口语映射到'综合所得·税率表'；
> **② 溯源**——回答必须带文号，检索给出'哪部法哪条'的证据链；
> **③ 可更新**——政策变了只换知识库，不动 prompt 和代码。"

### LLM Wiki 为什么没做（被追问时）

> "LLM Wiki 适合个人知识库的增量整理；我的场景要求**法规原文一字不差、可溯源**，wiki 化整理会引入摘要偏差、丢失精度——不做是为了**保真**。但我的轻量 JSON 关系索引（20 条规则两跳推理）已吸收了结构化关联思想，算轻量版 LLM Wiki。"

## 3. 技术选型话术卡

### 3.1 为什么 Qdrant 不是 X（选型四维度：部署形态 / 生态 / 检索能力 / 运维成本）

| 追问 | 回答 |
|------|------|
| 为什么不是 pgvector？ | ① BGE-M3 输出稠密+稀疏双向量，Qdrant 原生支持 sparse + RRF 融合，pgvector 不做稀疏向量，得自己造轮子；② 检索链路有 Layer 1 元数据预过滤（relevance_tier），Qdrant payload 过滤是原生能力，pgvector 要手写 SQL 组合。**诚实补充：2937 chunks 用 pgvector 也能跑，我选 Qdrant 省的是研发时间，不是数据量** |
| 为什么不是 Milvus？ | Milvus 是分布式架构（etcd+对象存储多组件），为亿级向量+高并发设计；数据量用它是杀鸡用牛刀，部署复杂度不值。真有那个规模，Qdrant 有云版可平滑演进 |
| 为什么不是 ChromaDB？ | 太轻：稀疏向量和元数据过滤能力弱，四层检索链路要求原生过滤，它撑不住 |
| 为什么不是 Pinecone？ | 闭源 SaaS、国内访问不便、按量计费贵；检索要自定义分层过滤，自托管可控性更重要 |
| 为什么不是 Faiss？ | Faiss 是相似度搜索**库**不是数据库——持久化、CRUD、元数据过滤全要自己写；Qdrant 直接给了 |
| 为什么不是 sqlite-vec？ | 不支持稀疏向量，只适合纯原型 |

**收尾句**："我按四维度对比过，Qdrant 是唯一混合检索开箱即用 + 单机 Docker 一条命令的方案。"

### 3.2 知识图谱：为什么不用 Neo4j

> "我评估过 Neo4j——知识图谱是 20 条关系规则、两跳推理，为它起一个图库服务 + 学 Cypher 是杀鸡用牛刀。JSON 关系索引可 git 版本化、可 review、热更新、零依赖。**等关系规模到百级、需要路径查询或图算法时，先迁 NetworkX（内存图算法库），再考虑图库**——按规模做决策。"

### 3.3 Redis 为什么不用

> "Redis 的价值是**跨服务节点的状态一致性**——缓存、分布式锁、会话级状态隔离。我的场景是单机单会话，没有跨服务问题；而且**用户记忆是资产，需要持久化，不能是可被 evict 的缓存**（记忆过期该 archive 不该删）。所以用 SQLite。未来多实例部署才引入 Redis 做分布式锁——现在引入是提前优化。"

### 3.4 模型分级为什么没做

> "选 DeepSeek V4 Flash 本身就是**分级思路的第一步**——主模型选便宜档；而且我刻意让**子 Agent 与主 Agent 同模型，避免工具协议漂移**（实测踩坑）。如果后续上意图改写/画像提取这种高频轻任务，会再加更小模型做预筛，把 flash 留给主推理。"

## 4. Multi-Agent 定位（核心防线，务必背熟）

### 4.1 架构定性

> "我的是**分层 Agent / Tool-as-Subagent 层级子代理**：主 Agent 按需把任务派给计税/社保子 Agent，子 Agent 结果回流主 Agent 统一决策——**信息通过主 Agent 汇聚流转，但子 Agent 之间不直接通信**。不直接通信是因为任务边界清晰、不需要协商。"

### 4.2 为什么这么设计（三个理由）

> "① **领域隔离**——两个子 Agent 有独立 prompt 和工具集，避免 prompt 互相污染（单 Agent 全做实测会串）；
> ② **容错设计**——降级机制（v1.4）：子 Agent 算不出结果卡时，复用 LLM 已生成的参数直调确定性引擎，功能不因子 Agent 失败而不可用；绕过检测（v1.5）：发现 LLM 心算数字就强制重算，数字必须来自引擎；
> ③ **可回退验证**——AGENT_MODE=tools 一键回退纯工具形态，用对拍评测（8/8）验证拆子 Agent 确实有收益。"

### 4.3 与 A2A / Multi-Agent 的区分（被追问时）

> "A2A 是谷歌推出的**对等通信协议**，Agent 之间地位平等、互相找对方协作（MCP 管 Agent-工具，A2A 管 Agent-Agent）。我的子 Agent 是**被调用的工具**，不是对等体。我评估过自由通信 Multi-Agent，结论是当前场景子任务边界清晰、不需要协商，做自由通信只会增加延迟和 token 成本——**这是我主动取舍，不是做不到**。"

### 4.4 是否需要自由通信 Multi-Agent（评估结论）

**结论：不需要。Tool-as-Subagent 是正确终点（"验证过的少量拆分"）。**

三标准逐项对照（全不满足）：

| 标准 | 场景 | 判定 |
|------|------|------|
| 天然可并行 | 用户一次只问一个问题，无并行需求 | ✗ |
| 信息量超上下文窗口 | 单问题信息量小，一个 Agent 轻松装下 | ✗ |
| 价值高、付得起数倍 token | 单用户场景，成本敏感 | ✗ |

四大功能全景判断：问答=主 Agent 本身；计算/社保=已有子 Agent（领域隔离）；申报指引=工具足够；**材料生成=纯确定性填表，最不该上 Agent**（字段映射 + openpyxl，上 Agent 反而引入幻觉风险）。

4 类"伪 Multi-Agent"信号澄清：并发→任务队列；批量→批处理；上下文长→压缩/摘要/分层检索（已有 guard+摘要）；**结果反复迭代喂给另一任务→唯一值得升级的信号，但先试单 Agent + 多工具**。

**话术三段式**：

> "我的评估结论是：不需要自由通信 Multi-Agent。判断依据是三个标准——可并行、超上下文、价值够高，我的场景全不满足。我做了 Tool-as-Subagent 分层，是因为计税/社保需要领域隔离（独立 prompt 和工具集，避免互相污染）和容错（降级 + 绕过检测），并且用 AGENT_MODE=tools 回退 + 对拍评测验证过拆分收益。如果未来出现需要多领域交叉协商的任务（比如家庭综合税务方案），我会先试单 Agent + 多工具，不行再升级——**按需演进，不提前堆复杂度**。"

## 5. 上下文工程

### 5.1 四层上下文

| 层 | 内容 | 触发 |
|----|------|------|
| 系统层 | system prompt（角色+规则） | 每轮 |
| 任务层 | 8 个工具描述 | 每轮 |
| 用户层 | SQLite 画像（城市/收入/扣除项/亏损） | 每轮注入 |
| 会话层 | 历史消息 + 40K 触发摘要（keep 20） | 超阈值触发 |

### 5.2 Prefix Caching（送分题）

> "我把**变化最少的内容放最前**：system prompt → 画像 → 工具描述 → 历史 → 当前 query，前缀缓存命中率高、token 成本低；画像更新频率低，不会频繁破坏缓存前缀。DeepSeek 上下文缓存自动生效。"

### 5.3 记忆三层（现有架构天然对应）

> "Working = 当前请求的 guard 瘦身结果；Short-term = 当前会话消息 + 40K 摘要；Long-term = user_contexts 画像。画像只记**事实型**结构化字段（字段级白名单），不记推导/偏好；写入时机是对话中显式提取回写；冲突按时间戳覆盖 + 保留历史。规划：偏好型加置信度+时效性标注、矛盾检测。"

## 6. 评测体系（碾压级优势，讲法比数字重要）

> "60 条测试 query 按 12 类税法场景构建，覆盖正常问答 + 边界情况（无前文口语提问、多条件组合）+ 对抗样本（诱导 LLM 心算、跨领域问题）；指标 Recall@5 / MRR / NDCG；run_all.py 一键回归，每次改 prompt 或检索参数后跑一遍防回归；**8 轮迭代 67.5%→85%，关键提升是文档级去重 + 评测集扩展**。生成层 LLM-as-judge：注意交叉评——judge 与干活模型分开（避免自家族偏好）、低温度、模型版本写死记录。"

---

## 7. AI 编码工作流（面试官最看重"过程"）

> "我是**文档先于代码**的 AI 协作：项目维护 40+ 份设计文档（PRD/架构/接口契约/评测标准），沉淀成 AI 编码上下文包，让 AI 不用重复探索；每个新模块**先定验收指标再编码**，评测驱动迭代。还有一条数据流水线：税总法规库下载 → 脚本清洗 → YAML 元数据 → 向量化，全程 AI 辅助。"

---

## 8. 五步踩坑叙事模板（17 项踩坑档案转面试资产）

> "第一版 RAG 检索 Top-5 混入无关条款（Recall 67.5%）→ 诊断发现是分块边界问题：硬按字符切分把法条切碎了 → 改成按`### 第X条`语义边界切分 + 文档级去重 + 评测集扩展到 60 条 → Recall 到 85%。重做的话，我会先建评测集再优化检索，而不是先优化再补评测。"

模板：**问题 → 诊断 → 方案 → 结果 → 重做会怎么改**（每个踩坑都按此五步讲）。

## 9. 安全（执行层兜底案例直接用）

> "我的注入面小：无用户文件上传、知识库全是官方清洗入库、工具是确定性计算不执行任意代码。但有一个**执行层兜底实战案例**：我发现 LLM 会在回答里绕过工具心算税额，所以加了正则检测 + 强制重算——这是 Prompt 层约束不住、执行层兜底的真实场景。安全边界必须做在执行层：工具参数校验、输出校验、审计日志。"

## 10. 观测与调试

**现状（2026-08-11 已落地）**：评测（批量对比）+ `chat.py` 工具审计日志（canary 检测 + 注入告警 + 工具调用清单）+ **`context/trace.py`**——JSONL 一行一事件（request_start / tool_call / tool_result / request_error / request_end），输出 `backend/data/trace/{日期}.jsonl`，集成耗时/字符数/工具清单统计。

**LangSmith 决策（不接，2026-08-11）**：

> "LangSmith 我知道——LangChain 官方的可观测平台，接上环境变量就自动 trace。但我的场景是单机演示，我评估过：① 演示要离线可控；② 数据不想上云；③ 我的 trace 需求很轻（每轮工具调用 + token），所以我**自己实现了轻量 JSONL trace**——成本更低、数据可控、每行都能讲清楚。等团队化开发、需要多人协作调试时，LangSmith 或 Langfuse（开源自托管，国内更友好）会是我第一个选的——现在用是提前优化。"

**金句**：改 Prompt 是猜，读 trace 是查。
